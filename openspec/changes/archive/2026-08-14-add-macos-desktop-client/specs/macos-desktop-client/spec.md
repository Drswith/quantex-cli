## ADDED Requirements

### Requirement: Desktop client MUST use the bundled CLI as its lifecycle boundary

The macOS desktop client SHALL invoke an architecture-matched bundled Quantex
CLI through a fixed native command boundary. It MUST NOT read or write Quantex
lifecycle state directly and MUST NOT accept arbitrary executable paths or
shell text from its web UI.

#### Scenario: Desktop refreshes managed updates

- **WHEN** the desktop requests an update snapshot
- **THEN** it invokes the bundled CLI in managed-only dry-run JSON mode
- **AND** it renders only the structured CLI result
- **AND** it does not mutate Quantex lifecycle state

### Requirement: Desktop updates MUST require explicit user confirmation

The desktop client SHALL require user confirmation before executing selected
agent updates and SHALL re-invoke the CLI for each selected agent.

#### Scenario: User confirms selected updates

- **WHEN** the user confirms one or more selected managed agents
- **THEN** the desktop runs their CLI updates serially
- **AND** each invocation uses the CLI lifecycle lock and current observation
- **AND** the desktop does not automatically update unselected agents

### Requirement: Desktop MUST cover the primary agent lifecycle

The desktop client SHALL let users browse the supported agent catalog, inspect
agent status and metadata, and invoke install, ensure, update, uninstall, and
execution workflows through typed native commands. Destructive or mutating
operations MUST require an explicit user action, and uninstall MUST require a
confirmation step.

#### Scenario: User manages an agent from its detail surface

- **WHEN** the user opens a supported agent in Desktop
- **THEN** the page shows its observed lifecycle status and relevant metadata
- **AND** only lifecycle actions valid for that status are offered
- **AND** the native host invokes a fixed bundled-CLI command for the selected action

#### Scenario: User runs an installed agent

- **WHEN** the user selects Run for an installed agent
- **THEN** Desktop opens the agent through Quantex in the macOS system terminal
- **AND** Desktop does not embed a terminal or accept shell text from the web UI

### Requirement: Desktop MUST expose diagnostics and Quantex configuration

The desktop client SHALL expose structured doctor and capabilities results and
SHALL read and edit supported Quantex configuration values through the bundled
CLI. It MUST distinguish Quantex configuration from Desktop-only preferences
and MUST NOT read or write Quantex configuration files directly.

#### Scenario: User edits Quantex configuration

- **WHEN** the user opens Quantex Settings and saves a supported value
- **THEN** Desktop validates the value and invokes the fixed structured CLI config command
- **AND** the refreshed value comes from the CLI result rather than an optimistic file write

#### Scenario: User reviews environment health

- **WHEN** the user opens Diagnostics or requests a refresh
- **THEN** Desktop renders structured doctor checks and detected capabilities
- **AND** failed checks retain actionable messages without exposing an arbitrary command runner

### Requirement: Desktop background operation MUST remain lightweight and user-controlled

The desktop client SHALL destroy its WebView when its main window is closed,
retain a tray-owned native host, and perform only configured managed-update
checks. It MUST default to daily checks and disabled login launch.

#### Scenario: User closes the desktop window

- **WHEN** the user closes the main desktop window
- **THEN** the window and WebView are destroyed
- **AND** the tray can reopen the window
- **AND** only the native host remains resident for configured checks

#### Scenario: A new update becomes available

- **WHEN** a completed background check finds a newly available agent version
- **THEN** the client emits one aggregate notification when notifications are enabled
- **AND** it does not execute an agent update

### Requirement: Browser UI development MUST use deterministic mock data

The Desktop workspace SHALL provide a browser-only Vite development mode that
uses deterministic mock inventory and preference data instead of native IPC.
Its UI SHALL use the default preset, theme tokens, and components generated by
the project-local official shadcn CLI rather than maintaining Desktop-specific
component implementations or a custom visual theme. Page composition MAY use
Tailwind utilities without modifying the generated component source.

#### Scenario: Developing Desktop UI in a browser

- **WHEN** a developer runs `bun run desktop:dev:web`
- **THEN** Vite renders a clearly labelled interactive mock inventory
- **AND** selecting and confirming mock updates never invokes Tauri or the CLI

#### Scenario: Reviewing the complete browser mock surface

- **WHEN** a developer opens the browser-only Desktop application
- **THEN** deterministic data exercises catalog, agent detail, lifecycle actions,
  diagnostics, Quantex settings, Desktop preferences, and recent activity
- **AND** the feature pages compose unmodified official shadcn components
- **AND** page code does not introduce a custom component theme or custom-sized controls

### Requirement: Desktop MUST keep self-upgrade and developer contracts out of scope

The desktop client SHALL NOT expose the bundled CLI's self-upgrade workflow or
developer-oriented `commands` and `schema` pages. Desktop application updates
and bundled sidecar replacement remain a separate signed application delivery concern.

#### Scenario: User reviews available Desktop actions

- **WHEN** Desktop renders navigation and settings
- **THEN** it does not offer a CLI self-upgrade action
- **AND** it does not offer command-registry or schema explorer pages
